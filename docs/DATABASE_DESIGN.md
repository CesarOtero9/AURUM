# AURUM — Database Design

**Version:** 0.1
**Status:** Initial database design
**Current phase:** Phase 3 — Technical Architecture

---

# 1. Purpose

This document defines the initial PostgreSQL database strategy for AURUM.

It translates the concepts defined in:

* `PRODUCT_VISION.md`
* `ARCHITECTURE.md`
* `TECHNICAL_ARCHITECTURE.md`
* `DOMAIN_MODEL.md`

into a relational persistence model.

This is not yet the final migration specification.

The purpose is to establish:

* table boundaries;
* key relationships;
* history strategy;
* fiscal/accounting precision;
* indexing principles;
* provenance;
* auditability;
* reprocessing support;
* data integrity.

---

# 2. Database principles

## 2.1 PostgreSQL is the structured operational source of truth

PostgreSQL will own structured AURUM state such as:

* CFDI facts;
* SAT observations;
* accounting records;
* reconciliation relationships;
* inference results;
* risks;
* jobs;
* audit history.

Original files may live outside PostgreSQL through the Document Center.

---

## 2.2 Original evidence must not be overwritten

The structured representation may evolve.

The original evidence must remain available.

Conceptually:

```text
Original XML
    ↓
Parser v1
    ↓
Structured representation

Original XML
    ↓
Parser v2
    ↓
New structured representation
```

AURUM must be able to explain which parser/rules produced a result.

---

## 2.3 Internal IDs and external identities are different

AURUM entities should normally use internal database IDs.

External identities remain business attributes.

Example:

```text
cfdi.id
+
cfdi.uuid
```

The UUID is the fiscal identity.

The internal ID is the database relationship identity.

---

## 2.4 Monetary precision

Fiscal and accounting values must use:

```text
NUMERIC
```

not binary floating-point.

Recommended starting precision:

```text
NUMERIC(20,6)
```

for values that may require SAT-level precision.

Some derived/display amounts may later use smaller scale where appropriate.

---

## 2.5 History must not be collapsed

Do not model:

```text
cfdi.estado_sat
```

as the only SAT source.

Use:

```text
sat_observations
```

and optionally maintain a current-state projection.

---

## 2.6 Many-to-many relationships must remain explicit

CFDI ↔ Policy must use a dedicated entity.

Do not add:

```text
cfdi.policy_id
```

as the primary accounting model.

---

# 3. Naming conventions

Initial database conventions:

* lowercase;
* snake_case;
* plural table names;
* singular semantic column names;
* timestamps ending in `_at`;
* foreign keys ending in `_id`.

Examples:

```text
cfdis
cfdi_concepts
sat_observations
policy_movements
cfdi_policy_links
```

---

# 4. Primary key strategy

Recommended initial strategy:

```text
BIGINT GENERATED BY DEFAULT AS IDENTITY
```

for internal relational IDs.

Reason:

* simple;
* efficient;
* readable;
* PostgreSQL-native;
* enough scale for AURUM.

UUID business values remain separate columns.

---

# 5. Time fields

Operational timestamps should use:

```text
TIMESTAMPTZ
```

when representing actual system events.

Examples:

* created_at;
* checked_at;
* imported_at;
* detected_at;
* completed_at.

Source fiscal timestamps may require preservation of original semantics.

For example CFDI issuance/stamping time may be stored separately from operational UTC timestamps.

# 19. SAT current state

Two acceptable strategies exist:

## Option A — Query latest observation

Advantages:

* no duplication;
* simplest truth model.

Potential disadvantage:

* heavier repeated queries at scale.

## Option B — Projection table

Example:

## cfdi_sat_current_states

```text
cfdi_id
latest_observation_id
fiscal_status
last_checked_at
changed_at
```

This acts as a projection/cache.

Historical `sat_observations` remains authoritative.

Initial recommendation:

**Use a current-state projection once monitoring is implemented.**

# 36. Risk deduplication

Risk generation must avoid creating the same active risk repeatedly on every evaluation.

Potential strategy:

Add:

```text
fingerprint
```

where fingerprint identifies the risk condition.

Possible uniqueness:

```text
UNIQUE(organization_id, fingerprint)
WHERE status IN ('OPEN', 'ACKNOWLEDGED', 'IN_REVIEW')
```

Exact design should be tested when Risk Engine is implemented.

Application logs do not belong in the relational domain model by default.

* stack traces;
* diagnostics;
* performance;

# 45. JSONB policy

JSONB should be used selectively.

Good candidates:

* inference score components;
* structured evidence metadata;
* provider raw responses;
* job configuration;
* result summaries;
* import statistics;
* audit metadata.

Bad candidates:

* core CFDI fields;
* policy movements;
* amounts required for reconciliation;
* relationships that need foreign keys.

Rule:

> Use JSONB for extensible metadata, not to avoid relational modeling.

# 48. Constraints and integrity

Database constraints should enforce structural integrity.

Examples:

* foreign keys;
* unique UUID;
* non-negative amounts where valid;
* valid month range;
* required references.

Complex fiscal/accounting decisions belong in domain logic.

Do not encode inference/classification logic into database triggers.

---

# 49. Cascades

Cascading deletes must be used conservatively.

Potential acceptable cascade:

```text
CFDI deleted
→ concepts
→ taxes
```

But authoritative fiscal records should rarely be physically deleted.

Therefore actual deletion strategy may favor:

* retention;
* deactivation;
* archival;
* explicit administrative cleanup.

Avoid broad `ON DELETE CASCADE` until record-lifecycle rules are understood.

---

# 50. Soft deletion

Soft deletion is not automatically required for every table.

Possible candidates:

* users;
* supplier profiles;
* configuration/catalog entries.

Historical tables such as:

* SAT observations;
* inference runs;
* audit events;

should generally remain immutable rather than soft-deleted.

---

# 51. Reprocessing strategy

Reprocessing must not destroy historical auditability.

Possible initial approach:

1. Preserve original XML document.
2. Update current structured CFDI representation transactionally.
3. Record parser version.
4. Record reprocessing audit event.
5. Preserve historical classification where required.

If full historical parser snapshots become necessary, introduce versioned extraction records later.

Do not overbuild this in V1.

---

# 52. Transaction boundaries

Important operations should be transactional.

Examples:

## CFDI ingestion

```text
CFDI header
+
concepts
+
taxes
+
complements
+
document association
```

should either persist coherently or fail coherently.

## SIF policy import

Policy + movement rebuild should avoid partially imported accounting records.

## Relationship confirmation

Relationship state + audit decision should remain consistent.

---

# 53. Bulk operations

AURUM must support large imports.

Use:

* batched inserts;
* bounded transaction sizes;
* efficient PostgreSQL operations;
* bulk repository methods;
* COPY where appropriate later.

Avoid:

```text
one commit per XML
```

for massive processing.

---

# 54. Duplicate CFDI behavior

When importing an already-known UUID:

Do not blindly create another CFDI.

The application should determine whether:

* document bytes are identical;
* a new PDF is available;
* source provenance differs;
* reprocessing is requested.

Possible result:

```text
CFDI already exists
+
new document/source association
```

UUID duplicate handling must be explicit.

---

# 55. File hash duplicates

SHA-256 may identify identical files.

But:

```text
same SHA-256
```

does not automatically imply the same business association should be removed.

It only means the bytes are identical.

Document deduplication and CFDI deduplication are different domains.

---

# 56. SAT observation retention

SAT observation history should be retained.

Future retention optimization may collapse excessive unchanged observations only if product/audit requirements justify it.

Initial recommendation:

**Preserve observations.**

Storage cost is relatively small compared with audit value.

---

# 57. Accounting import idempotency

Accounting imports must eventually carry source identity.

Potential identifiers:

* source file hash;
* import batch;
* external policy ID;
* mapping version.

Repeated import must not duplicate policies/movements blindly.

---

# 58. Legacy migration

Legacy data may later be migrated.

Migration should use dedicated provenance:

```text
LEGACY_MIGRATION
```

and ideally preserve:

* original legacy IDs;
* source system;
* migration batch;
* migration timestamp.

Do not let legacy IDs become AURUM primary keys.

---

# 59. Schema namespaces

Initial recommendation:

Use the default PostgreSQL application schema for simplicity.

Do not create many PostgreSQL schemas such as:

```text
cfdi.*
sat.*
accounting.*
```

during initial implementation unless a strong need appears.

Domain separation belongs primarily in application code.

Database schema namespaces may be introduced later if useful.

---

# 60. Enumerations

Avoid prematurely using PostgreSQL ENUM for every evolving business status.

Application-level enums persisted as constrained strings may be easier to migrate.

Examples:

```text
VARCHAR / TEXT
+
CHECK constraint where stable
```

Potentially stable statuses may later use PostgreSQL ENUM if justified.

---

# 61. Migration policy

All database changes must use Alembic migrations.

No undocumented manual schema edits.

Every migration should be:

* reviewable;
* reproducible;
* tested;
* reversible where reasonably possible.

---

# 62. Development database

AURUM should use PostgreSQL during development.

Avoid using SQLite as a substitute for important integration tests because PostgreSQL-specific behavior matters.

---

# 63. Test data

Tests should use sanitized/synthetic fiscal records.

Do not commit sensitive production data.

Maintain representative fixtures for:

* CFDI variants;
* SIF imports;
* policies;
* SAT provider responses;
* inference cases.

# 67. Risk relational map

          │

          │

* one policy;

The initial nullable FK approach is acceptable.

A generalized subject model may be considered later only if needed.

# 68. Audit relational strategy

`audit_events` may use:

```text
subject_type
subject_id
```

rather than dozens of nullable foreign keys.

Trade-off:

* flexible;
* weaker relational FK enforcement.

This is acceptable for audit metadata because AuditEvent is secondary historical metadata, not core relationship truth.

# 69. Database evolution strategy

AURUM should expect the model to evolve.

Rules:

1. Prefer additive changes.
2. Preserve original evidence.
3. Never discard historical observations casually.
4. Version rules producing derived results.
5. Use migrations.
6. Avoid premature optimization.
7. Benchmark before partitioning.

---

# 70. Partitioning

Do not partition tables initially.

Potential future candidates:

* audit_events;
* sat_observations;
* job_items.

Only consider PostgreSQL partitioning after actual scale/query patterns justify it.

---

# 71. Expected scale

AURUM should comfortably support:

* hundreds of thousands of CFDI;
* millions of concept/tax rows;
* large accounting movement histories;
* repeated SAT observations;
* multiple inference runs.

The proposed relational design can support this with appropriate indexing and batch processing.

---

# 72. Backup requirements

Once AURUM stores operational data, PostgreSQL backups become mandatory.

Future production design should include:

* automated backups;
* restore testing;
* document storage backups;
* migration safety.

Backup architecture is not required for initial local development.

# 74. Explicitly rejected database approaches

Do not flatten:

* taxes;
* payroll details;
* related UUIDs;

into numbered columns.

The XML may be preserved, but normalized fiscal facts need relational/queryable structure.

## 74.3 Current SAT state only

Historical observations must exist.

---

## 74.4 One policy per CFDI

Relationship must be N:N.

---

## 74.5 Inference score only

Structured evidence and historical runs must be retained.

---

## 74.6 Float for money

Use exact numeric precision.

---

## 74.7 Database triggers for business classification

Classification belongs in versioned domain/application logic.
